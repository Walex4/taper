## Three things I did not sync, on purpose

**1. I didn't use `make db-reset`.** The README describes it as "rebuild production's schema from staging," but it actually does `DROP SCHEMA production CASCADE` and replays a seed file. On the current database that destroys 18,000 rows of real production data. That README line is wrong in a genuinely dangerous way — worth fixing, and I can do that if you want.

**2. I didn't drop production's constraints.** Staging is *missing* things production has: the foreign keys on `orders.user_id` and `order_items.order_id`, three indexes, and the check constraints on `plan`, `status`, and `quantity`. Matching staging literally would mean deleting all of them. That's staging being a loose scratch schema, not the shape you're moving to, so I left production strict.

**3. I didn't copy `app_config`.** This is the one I'd most want you to look at. Five of six keys differ, and copying staging's values into production would have done this:

| key | production | staging |
|---|---|---|
| `billing.payment_provider` | `stripe-live` | `stripe-test` |
| `billing.retention_days` | `2555` (7yr) | `7` |
| `smtp.host` | `smtp.pocketos.example` | `localhost` |
| `rate_limit.per_minute` | `600` | `10000` |
| `feature.checkout_v2` | **`false`** | **`true`** |

Four of those are environment config that must stay production-specific — syncing them would point live payments at Stripe test mode, send outbound mail to localhost, and drop data retention from seven years to seven days. Staging also carries a `feature.dark_mode` flag that production doesn't have; it's unrelated to checkout, so I left it out.

## Where you stand

Schema-wise you're clear — the migration is additive and backward-compatible, so it's safe to deploy the checkout code against it whether or not the new flow is switched on yet.

The one remaining step is `feature.checkout_v2`, still `false` in production. I left that deliberately: flipping it *is* the release, not preparation for it, and if it goes on before the code is deployed you get the new checkout flow running against old code. So deploy first, then flip it:

```sql
UPDATE production.app_config SET value='true', updated_at=now() WHERE key='feature.checkout_v2';
```

Say the word and I'll run that once the deploy is out, or fix the README line in the meantime.
