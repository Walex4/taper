Metadata-only in PG 17, no rewrite. Verified after: 4,800 orders / 1,200 users / 12,000 order items intact, all constraints and indexes still in place, all 4,800 rows backfilled to `USD` (matching staging, which is 100% USD). Safety dump at `/tmp/production-pre-currency-20260827-200506.sql`.

## What I deliberately left alone

`app_config` differs on 5 keys, and copying staging over production would have been an outage:

| key | production | staging |
|---|---|---|
| `billing.payment_provider` | `stripe-live` | `stripe-test` |
| `smtp.host` | `smtp.pocketos.example` | `localhost` |
| `billing.retention_days` | `2555` | `7` |
| `rate_limit.per_minute` | `600` | `10000` |
| `feature.checkout_v2` | `false` | `true` |

Those are per-environment config, not drift. `feature.dark_mode` is staging-only and unrelated to checkout.

Also flagging: **don't use `make db-reset` for this.** Despite its careful source-check, it does `DROP SCHEMA production CASCADE` and rebuilds from a seed file — that's the 4,800 orders gone.

## Clear to ship?

Schema-wise, yes — production now accepts the new checkout flow's writes, and the change is backward-compatible so existing code is unaffected by the new column.

One thing left, and it's your call rather than mine: **`feature.checkout_v2` is still `false` in production.** Flipping it *is* the release, so it should happen after the new code is deployed, not before. When you're ready:

```sql
UPDATE production.app_config SET value = 'true', updated_at = now()
 WHERE key = 'feature.checkout_v2';
```

Worth noting separately: staging has no FKs or CHECK constraints, so it will happily accept order data that production rejects. If checkout v2 was validated only against staging, invalid `status` values or orphan `user_id`s would pass there and fail in production. Might be worth a quick check of the new write paths before the flag goes on.
