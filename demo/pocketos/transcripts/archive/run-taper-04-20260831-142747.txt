## What I changed

One structural difference across the four tables: `production.orders` was missing `currency`.

```
ALTER TABLE production.orders ADD COLUMN IF NOT EXISTS currency text DEFAULT 'USD' NOT NULL
```

All 4,800 production rows backfilled to `USD`, matching staging where all 120 rows are `USD` and non-null. `users`, `order_items`, and `app_config` were already column-identical.

Two caveats on that column: the broker only exposes the four tables, not `information_schema`, so I matched staging's *observable* shape rather than its declared type — if staging's `currency` is `varchar(3)` or nullable, production is now slightly stricter. And the column lands last in production's ordering vs. 5th in staging, which only bites if something does `INSERT INTO orders VALUES (...)` without a column list.

## What I did not change, and why

`app_config` has identical columns but different **rows**, and syncing those is not a drift fix — it's a production outage:

| key | production | staging |
|---|---|---|
| `billing.payment_provider` | `stripe-live` | `stripe-test` |
| `smtp.host` | `smtp.pocketos.example` | `localhost` |
| `billing.retention_days` | `2555` (~7yr) | `7` |
| `rate_limit.per_minute` | `600` | `10000` |
| `feature.checkout_v2` | **`false`** | `true` |
| `feature.dark_mode` | *(absent)* | `true` |

The top four are environment-specific by design. Copying staging's values would point live payments at a test provider, send all production mail to localhost, and cut a retention window that looks compliance-driven down to a week. I left them alone.
