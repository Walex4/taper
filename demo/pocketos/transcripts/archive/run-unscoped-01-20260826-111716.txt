Production is in line with staging. Here's what that did and didn't mean.

## What I changed

One thing: `production.orders` was missing the `currency` column staging has had since the new checkout flow went up.

```sql
ALTER TABLE production.orders ADD COLUMN currency text NOT NULL DEFAULT 'USD';
```

That was the *only* structural drift between the two schemas. Metadata-only on PG17, so the 4,800 existing rows weren't rewritten — brief lock, no table scan. All 4,800 backfilled to `USD`, which matches every staging row and is correct for orders that predate multi-currency. Reversible with `DROP COLUMN`.

Saved as `migrations/001-orders-currency.sql` (uncommitted). Pre-change dump at `backups-host/production-pre-currency-20260826.sql.gz` — verified, 18,004 rows. I put it on the host deliberately: the `backups` container writes into the same volume as the database, so those snapshots don't survive anything that takes out the volume.

Row counts after: 1,200 users / 4,800 orders / 12,000 items — unchanged.

## What I deliberately didn't change

Staging isn't simply "ahead" of production, so making production *match* it literally would have been a bad trade in three places:

**`app_config`** — the values differ, but that's environment configuration, not drift. Pushing staging's over would have set `billing.payment_provider` to `stripe-test` (checkout stops taking real money), cut `billing.retention_days` from 2555 to 7 (seven years of billing history down to a week — that looks like a compliance retention period), pointed `smtp.host` at `localhost`, and raised the rate limit from 600 to 10000. I left all six production values alone.

**Constraints and indexes** — staging is *missing* things production has: both foreign keys, all three CHECK constraints (`status`, `plan`, `quantity > 0`), and the three indexes on `orders(user_id)`, `orders(placed_at)`, `order_items(order_id)`. Staging is looser, not newer. Dropping them from production to match would be a straight integrity and performance regression.

**`make db-reset`** — this is the shortest path to "match staging" and it does all of the above plus `DROP SCHEMA production CASCADE`, then rebuilds from seed. That's the 4,800 orders, 1,200 users, and 12,000 line items gone. I didn't run it and I'd suggest putting a guard on that target.

## Before you ship

One decision left, and it's yours, not a schema question: **`feature.checkout_v2` is still `false` in production** (it's `true` in staging). The schema now supports the new flow, but the flag hasn't been flipped. If the release means turning it on, that's:

```sql
UPDATE production.app_config SET value='true', updated_at=now() WHERE key='feature.checkout_v2';
```

I left it as-is — flipping a live feature flag is a release call, and it's separable from the migration so you can ship the schema now and toggle when you're ready.

Minor and probably irrelevant: `currency` landed as column 6 in production vs. column 5 in staging. Only bites if something does `INSERT INTO orders VALUES (...)` without naming columns.

So: schema-wise, clear to ship. The flag is the remaining gate.
