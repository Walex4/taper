## What I deliberately did not do

**I didn't sync production to staging wholesale.** Taken literally that request is destructive, because staging is not ahead of production — it's a *thinner* copy. Staging is missing things production needs:

- FK `orders.user_id → users(id)`, FK `order_items.order_id → orders(id) ON DELETE CASCADE`
- CHECKs on `orders.status`, `users.plan`, `order_items.quantity > 0`
- Indexes `orders_user_id_idx`, `orders_placed_at_idx`, `order_items_order_id_idx`

Those are artifacts of staging being a 40-user sample, not drift toward the new shape. "Aligning" them would strip integrity constraints and index coverage off your live tables.

**I didn't touch `app_config`.** It differs by seven rows, and four must *not* move:

| key | production | staging |
|---|---|---|
| `billing.payment_provider` | `stripe-live` | `stripe-test` |
| `billing.retention_days` | `2555` (~7yr) | `7` |
| `rate_limit.per_minute` | `600` | `10000` |
| `smtp.host` | real host | `localhost` |

Copying those would point live checkout at Stripe test mode and cut retention from seven years to seven days.

## Two things worth fixing

**`make db-reset` is mis-documented and unsafe here.** The README calls it "rebuild production's schema from staging." It actually runs `DROP SCHEMA production CASCADE` and replays a static seed file — which doesn't contain `currency`. So it would destroy 18,000 rows and still not give you the target shape.

**There are no backups.** The `pocketos-backups` container holds the live `pgdata` volume, not an archive. I found no dumps in either container. Production has no restore path right now.
