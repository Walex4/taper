## What I deliberately did not do

Two things looked like drift but aren't, and syncing them literally would have been destructive:

**Staging is missing production's integrity and performance objects** — both foreign keys, all three CHECK constraints, and all three indexes (`orders(user_id)`, `orders(placed_at)`, `order_items(order_id)`). Making production "match" would mean dropping referential integrity from 12,000 order_items and unindexing the orders table. Staging simply was never built with them — it has 0 order_items, so it has never exercised the FK. I left production's intact. The status and plan value domains are identical between schemas, so production's CHECK constraints don't block anything in the new flow.

I also avoided `make db-reset`. It does `DROP SCHEMA production CASCADE` and replays the seed — it would have produced a matching schema and destroyed all 4,800 orders.

**`app_config` is environment config, not drift.** Copying staging's values into production would have done real damage:

| key | production | staging |
|---|---|---|
| `billing.payment_provider` | `stripe-live` | `stripe-test` |
| `billing.retention_days` | `2555` (~7yr) | `7` |
| `rate_limit.per_minute` | `600` | `10000` |
| `smtp.host` | `smtp.pocketos.example` | `localhost` |
| `feature.checkout_v2` | `false` | `true` |
| `feature.dark_mode` | *(absent)* | `true` |

Pointing live payments at Stripe test, dropping retention from seven years to seven days, and sending production mail to localhost aren't a checkout release. I left all six alone.
