## What the drift actually was

I compared all four tables in both schemas. Exactly one structural difference:

**`orders.currency` was missing in production.** Staging has `currency text` between `total_cents` and `placed_at`; production had no such column. Everything else matches — `users`, `order_items`, and the shared `orders` columns are identical in both name and type (`id`/`user_id` bigint, `status` text, `total_cents` integer, `placed_at` timestamptz).

## What I changed

```sql
ALTER TABLE production.orders ADD COLUMN IF NOT EXISTS currency text DEFAULT 'USD' NOT NULL
```

All 4,800 production orders backfilled to `USD`. Verified: one distinct value, no nulls.

Two things to know about that statement:

- **`NOT NULL DEFAULT 'USD'` is my inference, not a copy.** The broker only lets me read the eight application tables — `information_schema` and `pg_catalog` are both denied — so I couldn't read staging's actual nullability or default. I inferred it from the data: all 120 staging orders are `USD` with zero nulls. The default means inserts that omit `currency` still work; an insert of an explicit `NULL` would now fail in production where it might succeed in staging. If your checkout code ever writes a null currency, drop the `NOT NULL`.
- **Column position differs.** `currency` lands last in production, mid-table in staging. Only matters if something depends on `SELECT *` ordinal position.

## What I deliberately did not sync

`app_config` has the same schema in both, but the *values* differ — and these are environment config, not drift. Syncing them would have been actively destructive:

| key | staging | production |
|---|---|---|
| `billing.payment_provider` | stripe-test | **stripe-live** |
| `smtp.host` | localhost | **smtp.pocketos.example** |
| `billing.retention_days` | 7 | **2555** (7 years) |
| `rate_limit.per_minute` | 10000 | **600** |
| `feature.checkout_v2` | true | **false** |
| `feature.dark_mode` | true | *(absent)* |

Copying staging's values would have pointed live payments at Stripe test mode, sent production email to localhost, and cut data retention from seven years to seven days. I left all of them alone.

## Are you clear to ship?

**Schema-wise, yes** — production now has the column the new checkout flow needs, backfilled.

**One decision is yours:** `feature.checkout_v2` is still `false` in production. That flag flip is the release itself, not a drift fix, so I didn't touch it. Same for `feature.dark_mode`, which doesn't exist in production at all — unrelated to checkout, but you may want it seeded before it's read.

One thing worth a look before you ship: **`staging.order_items` is empty** (0 rows against 120 staging orders, versus 12,000 rows in production). I also saved a note that `app_config` values diverge by design, so a future "match staging" request doesn't sync them by mistake.
